# راه‌اندازی کلاس روی GitHub Pages و Google Sheets

## ۱. شیت خصوصی

با حساب مالک داده‌های کلاس یک Google Sheet جدید بسازید. در **Share**، دسترسی عمومی **Restricted** بماند. دانشجویان به خود شیت دسترسی ندارند. از **Publish to web** برای این شیت استفاده نکنید.

شناسهٔ شیت قسمت بین `/d/` و `/edit` در نشانی است. از **Extensions → Apps Script** پروژهٔ متصل را باز کنید.

## ۲. فایل‌های Apps Script

1. محتوای `apps-script/Code.gs` را در فایل کد `Code` بگذارید.
2. یک فایل **Script** با نام `Shared` بسازید و محتوای `apps-script/Shared.gs` را در آن بگذارید.
3. یک فایل **HTML** با نام `Bridge` بسازید و محتوای `apps-script/Bridge.html` را در آن بگذارید.
4. در **Project Settings**، نمایش manifest یعنی `appsscript.json` را فعال و محتوای فایل هم‌نام پروژه را وارد کنید.
5. همهٔ فایل‌ها را ذخیره کنید.

هر چهار فایل باید متعلق به همین نسخه باشند. `Shared.gs` از کد مشترک مرورگر ساخته می‌شود؛ آن را جداگانه ویرایش نکنید.

## ۳. Script Properties

در **Project Settings → Script Properties**:

| نام | مقدار |
|---|---|
| `SPREADSHEET_ID` | شناسهٔ شیت خصوصی |
| `STUDY_ID` | `minor-micro-1405-v1`؛ دقیقاً مطابق `config.js` |
| `ALLOWED_ORIGINS` | `https://javazali.github.io`؛ بدون اسلش انتهایی و بدون مسیر ریپو |
| `OPEN` | ابتدا `false`، برای پذیرش پاسخ `true` |
| `MAX_RESPONSES` | `150` |
| `START_AT` | اختیاری: زمان شروع، ISO 8601 |
| `END_AT` | اختیاری: زمان پایان، ISO 8601 |

نمونهٔ شکل زمان: `2026-11-01T09:00:00+03:30`؛ فقط نمونه است، تاریخ واقعی کلاس را خودتان تعیین کنید. برای نداشتن محدودیت زمانی، دو ویژگی زمان را نسازید.

برای تست محلی، موقتاً `ALLOWED_ORIGINS` را این‌طور تنظیم کنید:

```text
https://javazali.github.io,http://127.0.0.1:4173
```

پس از تست، origin محلی را حذف کنید. مسیر `/behavioral-lab/` جزئی از origin نیست.

## ۴. ساخت شیت‌ها و کدها

۱. در فهرست تابع‌های ویرایشگر، `setupLab_` را انتخاب و **Run** را بزنید. ورود و مجوز دسترسی را خودتان در صفحهٔ گوگل تکمیل کنید. اگر گوگل یا سازمان اجازه نمی‌دهد، نوع حساب و سیاست سازمان را بررسی کنید.

۲. دو برگه ساخته می‌شود:

- `Responses`: هر سطر یک پاسخ نهایی؛ هویت، نسخه، زمان‌ها، ترتیب و پاسخ‌ها.
- هر پرسش و هر الگوی تحلیلی هم ستون مستقل دارد؛ ستون‌های JSON نسخهٔ کامل پاسخ و ترتیب را نگه می‌دارند.
- `Participants`: فهرست خصوصی کدهای فعالیت و هش آن‌ها.

۳. تابع `createParticipantCodes_` را یک‌بار اجرا کنید. ۱۲۰ کد تصادفی ساخته می‌شود. اجرای دوباره، کدهای قبلی را پاک یا جایگزین نمی‌کند.

۴. یک کد به هر دانشجو بدهید. ستون `note` برای نگاشت خصوصی کد به دانشجو است. فهرست را در ریپو، گروه عمومی یا JavaScript نگذارید. در Responses فقط هش کد ذخیره می‌شود؛ کد خام برای توزیع در Participants خصوصی موجود است.

۵. هر کد و هر شمارهٔ دانشجویی فقط یک ثبت نهایی دارد. این کنترل تأیید رسمی هویت نیست.

## ۵. انتشار Web App و اتصال سایت

1. **Deploy → New deployment → Web app** را انتخاب کنید.
2. **Execute as: Me** و **Who has access: Anyone** را انتخاب کنید.
3. **Deploy** را بزنید و نشانی دارای پسوند `/exec` را بردارید. `/dev` عمومی نیست.

اگر Anyone برای حساب سازمانی وجود ندارد، سیاست حساب با این طرح سازگار نیست؛ از حساب مناسب تحت مدیریت مدرس یا راه مجاز سازمان استفاده کنید.

بازکردن مستقیم `/exec` پیام «از سایت مجاز وارد شوید» نشان می‌دهد؛ طبیعی است. اتصال از iframe سایت و با origin و شناسهٔ ارتباط انجام می‌شود.

در `config.js`:

```js
endpoint: 'https://script.google.com/macros/s/DEPLOYMENT_ID/exec',
```

شناسهٔ واقعی deployment را بگذارید. این URL عمومی است؛ رمز نیست. شناسهٔ شیت، کد دانشجویان و مجوز OAuth را در آن نگذارید.

تغییر را commit و push کنید و منتظر موفقیت Pages بمانید. `OPEN` را برای پذیرش پاسخ `true` کنید. تغییر properties نیاز به deploy جدید کد ندارد؛ تغییر کد نیاز دارد.

## ۶. تست پیش از کلاس

- با یک کد آزمایشی، از نشانی عمومی GitHub Pages شروع کنید و همهٔ ۲۰ سؤال را پر کنید.
- فقط پس از تأیید ثبت باید گزارش باز شود؛ شیت باید **یک سطر** تازه داشته باشد.
- رفرش گزارش و تلاش مجدد نباید سطر تکراری بسازد.
- زیر ۵ پاسخ، نمودار پنهان است؛ با ۵ ثبت معتبر، نمودار واقعی ظاهر می‌شود.
- کد اشتباه یا کد استفاده‌شده برای شناسهٔ دیگر باید رد شود.
- با `OPEN=false` پاسخ تازه رد می‌شود؛ تکرار همان ثبت قبلی می‌تواند تأیید قبلی بگیرد.
- دسترسی روی اینترنت دانشگاه و موبایل به GitHub Pages، `script.google.com` و `googleusercontent.com` را بررسی کنید.
- چند ثبت تقریباً هم‌زمان روی محیط پایلوت جدا امتحان کنید. تست mock تضمین ظرفیت واقعی گوگل نیست.

برای پایلوت و کلاس بهتر است دو شیت و دو پروژهٔ Apps Script جدا داشته باشید. برای مطالعهٔ جدید، `STUDY_ID` سایت و گوگل را با هم تغییر دهید و محیط جدید بسازید.

## رفع اشکال

| نشانه | بررسی |
|---|---|
| سایت آزمایشی است | `endpoint` خالی است یا Actions هنوز منتشر نشده است. |
| خطای اتصال | URL حتماً `/exec`، دسترسی Anyone، origin دقیق و هر چهار فایل در نسخهٔ deployment باشند. |
| iframe بار نمی‌شود | مجوز سازمان، افزونهٔ مسدودکننده، سیاست کوکی/مرورگر و دسترسی به دامنه‌های گوگل؛ مرورگر دیگر را هم امتحان کنید. |
| رفتار کد قدیمی است | Deploy → Manage deployments → Edit → New version → Deploy. |
| خطای نسخه | `STUDY_ID` و `LabData.version` سایت و Shared.gs باید برابر باشند. |
| کد صحیح رد می‌شود | Participants و هش‌ها را بررسی و پس از تغییر دستی، `clearLabCache_` را اجرا کنید. |
| آمار تازه نیست | کش تا ۳۰ ثانیه؛ فاصلهٔ تازه‌سازی مرورگر ۶۰ ثانیه. |
| شلوغی سرویس | با همان شناسه دوباره ثبت کنید؛ Executions و سهمیه‌های Apps Script را بررسی کنید. |

بودجهٔ نوشتن ۱۸۰ ثبت در دقیقه، سقف کلی ۱۵۰ پاسخ و کدهای ۱۲۰ نفره، کنترل کاربردی‌اند؛ دفاع قطعی در برابر سیل درخواست نیستند. درخواست ردشده هم می‌تواند ظرفیت اجرای گوگل مصرف کند.

## اصلاح و حذف توسط مدرس

پاسخ نهایی در سایت قابل ویرایش نیست. در صورت ضرورت، مدرس سطر را در شیت خصوصی حذف و `clearLabCache_` را اجرا می‌کند. شرکت‌کننده در مرورگر دارای تأیید قبلی باید داده‌های همین سایت را پاک کند تا تجربهٔ جدید بسازد. برنامهٔ نگهداری و حذف داده را مدرس به دانشجو اعلام می‌کند.

## خط فرمان برای دفعات بعد

با ابزار رسمی `clasp`، خودتان یک‌بار `clasp login` را انجام دهید و Apps Script API حساب را فعال کنید. `.clasp.json` محلی را به پروژهٔ درست متصل کنید. فایل ورود و توکن را commit نکنید؛ `.gitignore` آماده است. این روش برای راه‌اندازی اول ضروری نیست.
